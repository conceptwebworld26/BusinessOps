### What the repository holds (verified at `75ced03`, 2026-09-19)

1. **`tests/fixtures/` holds builder code only.** `git ls-files tests/fixtures` lists `__init__.py` and eight
   `build_*.py` modules, and no data file. Each builder writes into a directory its caller supplies. Their docstrings
   say so:
   - `build_fixtures.py`: "Built in a temporary directory at test time rather than committed";
   - `build_quality_fixtures.py`: "Built at test time in a temporary directory";
   - `build_m13_large_fixtures.py`: "written into a caller-supplied temporary directory and are never committed".
2. **"Fixtures M13.1 generated" is an empty set of files.** The M13.1 development record
   (`2026-09-18-m13-1-deterministic-hardening.md`) states: "The D1 fixtures were generated in temporary directories and
   deleted by the tests." M13.1 committed one builder, `build_m13_large_fixtures.py`, and no data.
3. **`assets/demo-data/` holds one dataset**: `northwind_sales.csv` and `.xlsx` (the same business),
   `business_context.json` and the generator. The CSV has 2,204 data rows over 24 monthly periods (2024-01 to 2025-12)
   and a clean header. `integration.test_anomaly_m8.…test_the_demo_dataset_scans` asserts that
   `anomaly-detection` over it returns status `ok` with flagged anomalies. So it maps without clarification, is not
   `CRITICAL`, and does contain flagged anomalies.
4. **M13 may not add to `assets/demo-data/`** (§A.3).
5. **The forecast minimum is 12 periods by default** (`lib/python/biq/forecast/engine.py`, `min_history_periods`).
6. **The engine behaviour already exists and is tested deterministically**, using builder output written at test
   time:
   - ambiguous mapping: `build_fixtures.ambiguous_mapping`, coverage row S1-14;
   - `CRITICAL` halt: `build_fixtures.critical_*`, the deterministic support for S3-02;
   - short history: `build_forecast_fixtures.short` (four months), coverage row S1-09.
7. **Line endings of committed text files depend on the checkout.** This repository has no `.gitattributes`, and
   `core.autocrlf` is `true` on the development machine. `git ls-files --eol` shows `northwind_sales.csv` as `i/lf
   w/crlf`: LF in the index, CRLF in this working tree. A committed CSV's working-tree bytes therefore depend on the
   git configuration of the machine that checked it out.
8. **No product path reads `tests/`.** A search of `lib/`, `skills/`, `commands/`, `agents/`, `reference/`, `config/`
   and `.claude-plugin/` finds no reference to `tests/fixtures`.

### G-1 verified

1. **ADR-0039 restricts eval inputs** to `assets/demo-data/` and "fixtures M13.1 generated" (§E.2), and restricts
   input paths to `assets/demo-data/` or `tests/fixtures/` (§E.5).
2. **Three `behaviour` cases (S3-01, S3-02, S3-03) need an input that no acceptable committed file provides.** The
   demo dataset cannot express their preconditions, M13 may not add to it (§A.3), and M13.1 committed no data. S3-04
   and S3-05 do not need a new input.
3. **The existing builders are not valid eval inputs.** A builder is Python source, not a dataset. A case that named
   one would require something to execute it to produce the input.
4. **Generating the input at execution time is not permitted.** A scaffold may do "nothing but copy repository
   synthetic inputs" (§F.6). The only Bash grant is for running the engine (§F.5). §E.5 requires the input path to
   exist in the repository. An operator generating files by hand before a run would produce an input that is neither
   in the repository nor reproducible from it.
5. **The gap is in the permitted-input rule, not in the product.** The behaviour exists and is deterministically
   tested (fact 6). Only a committed, contract-valid input for the eval cases is missing.

## Problem

Define how the input fixtures M13.2's eval cases need may be created, stored, bound to their cases and statically
validated, so that M13.2 can be implemented. The rule must not admit arbitrary generated or runtime data, must not
weaken any ADR-0039 safety or reproducibility rule, and must not change product behaviour.

## Options considered

### Option A — Name a builder module as the case input and let the case run it

**Rejected.** A builder is code, not an input (G-1 finding 3). Running it inside an eval needs either a scaffold that
does more than copy (§F.6 prohibits it) or a Bash grant beyond the engine (§F.5 prohibits it). The input would be
generated at execution time, which is the workaround G-1 finding 4 rules out.

### Option B — Add the fixtures to `assets/demo-data/`

**Rejected.** §A.3 prohibits M13 from changing `assets/`. The demo dataset is the product's single shipped example,
and planting broken, ambiguous or truncated files in it would change what users see.

### Option C — Generate the fixtures into a temporary directory immediately before each run

**Rejected.** The input would not be repository-owned. §E.5 could not check it, and a reviewer could not tell whether
the file a run consumed was the one the builder defines.

### Option D — Rewrite the cases so the demo dataset suffices

**Rejected.** The demo file cannot be made ambiguous, `CRITICAL` or four periods long without changing it (§A.3).
Asking the model to discard periods or columns would test a different behaviour from the one §E.3 names.

### Option E — Committed, builder-reproduced, manifest-bound input fixtures in a dedicated subdirectory of `tests/fixtures/`

**Chosen.** The location is already inside ADR-0039's approved scope (§A.2) and its path rule (§E.5). The files are
committed, so a case consumes exactly what the repository holds. The builder and a byte-identity check make every file
reproducible and detect drift. The manifest makes the binding between each file and its case explicit and checkable.

## Decision

**M13.2 eval cases may consume committed, synthetic, deterministic input fixtures stored under
`tests/fixtures/eval_inputs/`, each reproduced byte for byte by a builder in `tests/fixtures/`, recorded in a
manifest, and bound explicitly to the cases that consume them. A fixture is an input, never an answer. The eval
consumes the committed file and never generates a replacement at execution time. Nothing in this ADR authorises
execution, changes the execution policy, or changes product behaviour.**

### 1. Location

- Committed eval input fixtures live under **`tests/fixtures/eval_inputs/`**. This is a subdirectory of the location
  ADR-0039 already approves (§A.2, §E.5), not a new location. It exists so that the path alone tells a committed eval
  input apart from builder code. `tests/fixtures/` remains a Python package of builders, and a builder is never an
  eval input.
- `assets/demo-data/` remains a permitted input location, unchanged, and is read-only to M13 (§A.3). **A fixture is
  admissible only where `assets/demo-data/` cannot establish the case's input precondition**, and the manifest states
  why (§4). On the evidence above, that is S3-01, S3-02 and S3-03. S3-04 uses the demo file, and S3-05 needs no file.
- No other location may supply an eval input. In particular, a case may not use a file under `evals/`, the session
  scratchpad, a temporary directory, the user's home directory or any path outside the repository.
- `tests/fixtures/eval_inputs/` holds only fixture files, the manifest (§4) and one `.gitattributes` file (§3). A
  sub-subdirectory needs a further decision.

### 2. Synthetic-data boundary

- Every fixture is synthetic, and is invented for the case. No customer, employee, user, production, connector,
  connected-system, vendor or other confidential data may appear, and nothing may be copied from, shaped after or
  named after real data (ADR-0039 §C.2 and §I, applied unchanged).
- Every identifying text value, such as a customer, product, region or salesperson name, uses the obviously
  synthetic `Synthetic …` form of `build_m13_large_fixtures.py` (for example `Synthetic Customer 01`).
- No fixture contains a URL, an email address or a hostname, except on the reserved domains `example.com`, `.invalid`
  or `.example`. It contains no token-shaped string and no credential.
- The format is **CSV only**, with ASCII content. Any other format, including `.xlsx` and `business_context.json`,
  needs a further decision.

### 3. Determinism

- The same builder always produces a **byte-identical** file: across runs, machines and supported Python versions
  (3.9+).
- The builder uses only literal values and integer or `decimal.Decimal` arithmetic. It uses:
  - no random number generator, seeded or not;
  - no clock, timestamp, `date.today()` or `datetime.now()`;
  - no environment variable, platform query, locale, user name or path in the output;
  - no network access, and no file read of any kind.

  Binary floating point is not used to produce any written value.
- The builder fixes the encoding (UTF-8, no byte-order mark, ASCII content) and the line terminator (`\n`)
  explicitly. It never relies on a platform default.
- **Line endings are pinned in git.** `tests/fixtures/eval_inputs/.gitattributes` marks every file in that directory
  `-text`. Git then stores and checks out the builder's bytes unchanged under any `core.autocrlf` (fact 7). The file
  sits inside the fixture directory. The repository root, `.gitignore` and every other path are unaffected.
- No fixture file, and no manifest entry, carries a timestamp. When a fixture was created is recorded by git and by
  the development record that creates it.

### 4. Builder and provenance

- **The builder** is one new module, `tests/fixtures/build_eval_inputs.py`. It has one function per fixture, each
  taking an output directory and returning the path it wrote. It may import from other `tests/fixtures/` builders
  only if the imported code meets §3. It writes only into the directory its caller supplies, and has no default
  output location.
- **The manifest** is `tests/fixtures/eval_inputs/manifest.json`, which the standard library can parse, unlike YAML.
  It holds one entry per fixture, and every field is required:

  | Field | Content |
  |---|---|
  | `path` | Repository-relative path of the committed file |
  | `builder` | `tests/fixtures/build_eval_inputs.py:<function>`, with any arguments |
  | `sha256` | SHA-256 of the committed bytes |
  | `bytes` | Size of the committed file in bytes |
  | `format` | `csv` |
  | `line_terminator` | `\n` |
  | `precondition` | The input property the fixture establishes, such as "four monthly periods". It describes the input, never the expected behaviour (§6) |
  | `why_not_demo_data` | Why `assets/demo-data/` cannot establish the precondition (§1) |
  | `cases` | The eval case directories that consume the fixture, one or more |
  | `synthetic` | The statement that every value is synthetic, under ADR-0041 §2 |

- **Creation.** A committed fixture is created by running its builder into a temporary directory and adding the result
  as a new file. Changing a committed fixture later changes the input of every case bound to it. It needs the explicit
  approval `CLAUDE.md` §9 requires for overwriting a file, and it is recorded in a development record with the old and
  new `sha256`.
- **Verification.** The §E.5 validator rebuilds every manifest entry into a temporary directory and asserts that the
  bytes are identical to the committed file, and that the committed file matches the manifest's `sha256` and `bytes`
  (§8). A builder change that alters a committed fixture therefore fails deterministically until the fixture and
  manifest are deliberately updated.

### 5. Case binding

- **Every eval case names each of its input files explicitly**, by repository-relative path, in its own case files.
  A path is either under `assets/demo-data/` or recorded in the manifest.
- **Binding runs both ways.** Every fixture path a case names is bound to that case in the manifest's `cases`. Every
  case in a manifest entry names that fixture.
- A case consumes nothing it does not name. It does not read a directory, match a file pattern, or pick up a file by
  its location.
- Every manifest entry is bound to at least one case. No committed fixture is left orphaned.
- The manifest, the builder and `.gitattributes` are **never** eval inputs. They are not named by a case and not
  copied into an eval sandbox.

### 6. Input semantics — a fixture is an input, never an analytical result

- A fixture holds the raw data that establishes a precondition, such as ambiguous headers, a `CRITICAL` defect or
  four periods. It holds nothing the evaluated behaviour is supposed to produce.
- A fixture contains no expected output, verdict, answer, explanation, instruction, precomputed KPI, forecast,
  quality grade, anomaly label or refusal text. It contains no column or value whose name or content states what the
  model should do, such as `Expected`, `Answer` or `Ambiguous`.
- Raw per-row fields that a sales extract ordinarily carries, such as `NetRevenue` or `CostOfGoods` per line, are
  inputs and are permitted.
- No literal string that a deterministic grader asserts on, for a case bound to a fixture, appears in that fixture.
- The `precondition` field describes the input for reviewers. It is not an eval input (§5).

### 7. Small and purpose-built

- Each fixture has the fewest rows and columns that establish its precondition through the unchanged product
  pipeline. Beyond its precondition, it carries nothing that would trigger a second, unrelated behaviour, so that the
  case isolates one behaviour.
- **Each fixture is at most 16 KiB.** This ceiling applies to fixture files only. It is not a measurement threshold
  and it changes no product or test limit.
- `tests/fixtures/build_m13_large_fixtures.py` is the M13.1 measurement generator (§D.1). It is not an eval-input
  builder, and its output is never an eval input.
- One fixture may serve several cases only if each case needs exactly its precondition.

### 8. Static validation — the §E.5 validator gains these assertions

`tests/unit/test_m13_eval_cases.py`, the module §E.5 already names, still reads case files as text and parses no YAML.
Its existing assertions stay, with the second one amended (§10). It gains these, all deterministic and offline:

1. Every input path a case names exists in the repository and lies under `assets/demo-data/` or
   `tests/fixtures/eval_inputs/`.
2. The manifest parses with `json`, has every §4 field in every entry, and lists exactly the files present in
   `tests/fixtures/eval_inputs/` other than itself and `.gitattributes`.
3. For every manifest entry, the builder reproduces the committed file byte for byte in a temporary directory, and
   the committed file matches `sha256` and `bytes`.
4. The case-to-fixture binding holds both ways (§5), and no manifest entry is orphaned.
5. The builder module reads no file, and imports or calls no network, random, clock, environment or subprocess
   facility. The validator checks this by reading its source.
6. No fixture contains a URL, email address or hostname outside the reserved domains, or a token-shaped string (§2).
   Every fixture is ASCII, uses the `\n` line terminator and is at most 16 KiB (§2, §3, §7).
7. `tests/fixtures/eval_inputs/.gitattributes` exists and marks the directory's files `-text`.
8. No literal string a deterministic grader asserts on for a case appears in a fixture bound to that case (§6).
9. No case names a builder, the manifest, `.gitattributes`, or a path produced at run time as an input.
10. No scaffold script writes a file other than by copying a named input from `assets/demo-data/` or
    `tests/fixtures/eval_inputs/`. This restates §F.6, which already requires it, for the new location.

Together these establish that every case input exists, lies in an allowed repository location, is repository-owned,
comes from no forbidden external source, and needs no runtime network retrieval or runtime generation.

This ADR does not implement the validator. It is implemented in M13.2, under M13.2's own prompt.

### 9. How a committed fixture reaches an eval

- The case consumes the **committed** file. Nothing generates, regenerates, downloads or repairs an input at eval
  execution time.
- Any delivery of an input into the eval sandbox is governed by §F.6, unchanged: a scaffold may only copy a
  repository synthetic input, and `tests/fixtures/eval_inputs/` files are repository synthetic inputs under this ADR.
  No scaffold, grant or tool may run a builder.
- This ADR does not decide the delivery mechanism beyond that, and adds no grant. The platform's current behaviour is
  a G-3 matter (§12).

### 13. No production impact

Every file this ADR admits lies under `tests/fixtures/`. No product component reads `tests/` (fact 8). The fixtures
change no command, skill, agent, engine module, reference document, configuration, schema, manifest or `.mcp.json`,
and the nested `.gitattributes` changes how git stores files in its own directory and nowhere else. No BusinessIQ
output changes.

## Reason

G-1 is a gap in the contract, not in the product. The deterministic suite already exercises all three missing
preconditions with builder output (fact 6). The eval cases lack only a committed, contract-valid file to name. The
chosen option closes that gap in the location ADR-0039 already approves. It keeps every property that made §E.2 and
§E.5 safe: inputs are synthetic, repository-owned and statically checkable, and none is generated at run time.

Each rule closes a specific way the amendment could be abused:

- the demo-data necessity test (§1) stops fixtures from multiplying where the shipped dataset serves;
- byte-identity and the manifest (§3, §4) stop a committed file from drifting away from its builder unnoticed;
- the two-way binding (§5) stops a case from consuming anything it does not declare;
- the input-only rule (§6) stops a fixture from carrying the answer a grader looks for;
- the `.gitattributes` pin (§3) stops byte-identity from depending on a contributor's git settings, which this
  repository demonstrably varies on (fact 7).

## Consequences

**Positive**

- S3-01, S3-02 and S3-03 can be authored against inputs the repository owns and a reviewer can reproduce.
- A committed input that drifts from its builder, or that nobody uses, fails the deterministic suite.
- The execution policy, evidence vocabulary and completion gate are untouched.

**Negative**

- Three small committed data files, a builder module, a manifest and a `.gitattributes` file are added to maintain.
- The byte-identity check couples the committed fixtures to the builder. A deliberate change to either needs both
  updated in the same change.
- The builder may not reuse the existing float-formatting builders unchanged (§3). It restates similar shapes with
  integer or `Decimal` arithmetic. This is a second implementation of the same preconditions, accepted for byte-level
  determinism.

## Revisit when

- A case needs an input format other than CSV, or a sub-subdirectory under `tests/fixtures/eval_inputs/`.
- A fixture cannot establish its precondition within 16 KiB.
- `assets/demo-data/` changes in a way that affects the §1 necessity test for a bound fixture.
- The platform delivers eval inputs in a way that §9 and §F.6 do not describe, as observed at the G-3 pre-flight.
- A milestone after M13 needs eval fixtures. It needs its own decision, because this ADR does not extend beyond M13.
